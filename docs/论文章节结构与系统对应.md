##### 3.3.2 面向演示页面的中间表示构建算法

> 对应代码：`outline_generator.py`（Step 4）+ `slide_pool_builder.py`（Step 5）

**（1）方法理论**

- 从章节语义空间到页面语义空间的粒度转换：fsir:S→Z={z1,...,zK}*f**s**i**r*:S→Z={*z*1,...,*z**K*}
- 演示单元（SIR）的结构设计——7 个核心字段：

| 字段             | 作用                     |
| ---------------- | ------------------------ |
| `slide_id`       | 全局唯一编号，跨章节追踪 |
| `slide_title`    | 页面主题                 |
| `section_name`   | 来源章节，保持可追溯性   |
| `role`           | 整体叙事角色（14 种）    |
| `slide_purpose`  | 局部表达目的             |
| `content_points` | 核心要点集合             |
| `visual_refs`    | 图/表/公式完整引用数据   |

- `role` 与 `purpose` 的双层叙事建模：Narr(zk)=⟨rolek→Global Function, purposek→Local Intention⟩*N**a**rr*(*z**k*)=⟨*ro**l**e**k*→Global Function, *p**u**r**p**os**e**k*→Local Intention⟩
- 视觉引用回填的设计思想：大纲生成阶段只输出 ID 引用，池化阶段将 ID 解析回完整数据（路径、标题、分析文本），使 SIR 成为自包含的数据合约

**（2）算法实现**

- 大纲生成（`outline_generator.py`）：`_build_element_map()` 建立视觉分析索引 → `_prepare_sections()` 组装 `{abstract, section_name, content, refs}` → 逐章节调用 Dify workflow#3 → 输出 `ppt_outline` 数组
- 素材池构建（`slide_pool_builder.py`）：`_normalize()` 健壮解析 LLM 输出（处理字符串包裹、markdown 围栏、嵌套 text 键）→ `_build_visual_refs()` 回查章节树和视觉分析结果，补全完整元素数据 → 分配全局递增 `slide_id`

##### 3.3.3 面向演示叙事的逻辑重构算法

> 对应代码：`narrative_reorder.py`（Step 6）

**（1）方法理论**

- 约束驱动叙事重排策略：先满足硬约束（叙事骨架不断裂、视觉证据不丢失），再在自由度内优化信息密度
- 优先级体系：视觉完整性>叙事下限>锚点角色完整性>信息密度优化视觉完整性>叙事下限>锚点角色完整性>信息密度优化
- 14 种叙事角色与载荷权重体系：method_component(1.45)、theoretical(1.60) 等高价值角色获得更高保留优先级
- 七段式叙事弧模型：opening → problem → related → thesis → method → evidence → closing，每段有目标占比和最小/最大页数约束
- 保留分数（keep_score）：Score(zk)=wk×(1.0+0.3×Ck+0.2×Vk)*S**core*(*z**k*)=*w**k*×(1.0+0.3×*C**k*+0.2×*V**k*)

**（2）算法实现**

三遍算法：

| 遍次   | 操作                | 关键逻辑                                                     |
| ------ | ------------------- | ------------------------------------------------------------ |
| Pass 1 | 角色分组            | 14 角色 → 7 叙事组映射                                       |
| Pass 2 | 预算分配 + 组内压缩 | 载荷比例动态预算 + floor/cap 约束；视觉钉扎 → 标题去重 → Jaccard 合并（阈值 0.25）→ keep_score 裁剪；锚点角色补位 |
| Pass 3 | 全局排序            | 组间按叙事弧顺序；组内按 (角色优先级, 章节推进序, -keep_score) 三元组排序 |

### 4.2 问题分析（仅分析问题，不涉及解法）

- **4.2.1 纯文本页面的视觉表达不足问题**
  叙事重构输出的候选页面中，大量页面仅包含文本要点和叙事角色标注，缺乏图、表等视觉锚点。在演示场景中，这类页面容易退化为"标题 + 线性列表"，缺乏视觉层次感和快速可扫描性。
- **4.2.2 视觉元素引入后的图文信息冗余问题**
  当系统为纯文本页面补充示意图后，原始文本要点中描述的结构关系已被图像承载，若不对文本进行相应调整，将出现图文重复表达、页面信息拥挤的问题。
- **4.2.3 异构内容到统一页面的渲染适配问题**
  经过增强后的页面集合包含多种内容类型（论文原图、AI 生成图、纯文本要点、表格、公式），且各页面承担不同叙事角色，如何在统一的模板体系下为每种内容类型匹配最合适的页面布局，并生成符合学术规范的可执行 HTML 页面，是从结构化表示到最终交付物的最后一环。

### 4.3 基于多模型协同的视觉增强与页面生成算法

#### 4.3.1 基于规则路由的视觉增强策略分类算法

**（1）方法理论**

说明为什么采用**规则决策树**而非 LLM 来完成策略分类：

- 分类维度有限且明确（视觉状态、要点数量、数学密度、叙事角色），不需要深层语义推理
- 规则路由可解释、可调试、零延迟，适合作为流水线中的轻量级路由节点
- 输出为三种策略之一：**skip**（已有视觉元素，不干预）、**image**（生成示意图 + 重写要点）、**css**（分配 CSS 布局策略）

决策优先级体系的设计依据：

已有视觉>内容特征（要点数、数学密度）>角色类型映射>默认策略已有视觉>内容特征（要点数、数学密度）>角色类型映射>默认策略



- 已有图/表/公式的页面直接跳过，避免覆盖论文原始证据
- 要点过少（≤2）或数学密集（≥50%含数学符号）的页面不适合图像补全，走 CSS 增强
- 分析性角色（experiment_setup, analysis_ablation, theoretical）需要精确数据呈现，走 CSS 增强
- 叙事性角色（hook_context, method_overview, insight_thesis 等）内容更适合图示化表达，走图像增强

**（2）算法实现**

`classify(slide)` 决策树的完整流程、`_IMAGE_ROLES` 映射表（7 种角色→图像类型）、`_CSS_STRATEGY` 映射表（5 种角色→CSS 策略 + 默认 `structured_bullets`）、`_is_math_heavy()` 数学密度检测函数。

#### 4.3.2 基于图像生成与文本重写的视觉补全算法

**（1）方法理论**

**角色—图像类型映射的设计依据**：不同叙事角色对应不同的最佳视觉表达形式。论述 7 种映射关系的认知依据：

| 叙事角色           | 图像类型                     | 认知依据                       |
| ------------------ | ---------------------------- | ------------------------------ |
| hook_context       | concept_diagram（概念图）    | 开场建立概念关联网络           |
| gap_limitations    | comparison_chart（对比图）   | 现有方法与目标之间的差距可视化 |
| problem_definition | directed_graph（有向图）     | 问题结构的节点-关系表达        |
| insight_thesis     | framework_diagram（框架图）  | 核心思想的模块化表达           |
| method_overview    | flowchart（流程图）          | 方法流程的分步展开             |
| related_work       | timeline_diagram（时间线图） | 研究脉络的时序梳理             |
| takeaways          | infographic（信息图）        | 关键结论的强调性呈现           |

**学术示意图的视觉约束**：平面矢量风格、BIT 配色体系（主色 #2B4663、辅色 #5C7885、点缀 #B9CAE1）、白色背景、几何形状 + 标签 + 连接箭头、480×420 画布尺寸。

**图文互补的文本重写原则**：图像生成后，原始文本要点中与图像表达重叠的结构性描述应被压缩，保留的文本应**补充**图像而非重复。目标要点数根据原始数量动态调整（≤4 条→保留 2 条，>4 条→保留 3 条）。

**（2）算法实现**

- `_build_image_prompt()`：组装 Gemini 生成 prompt（标题、目的、角色、要点概念、BIT 配色约束、图像类型引导语 `_image_type_guide()`）
- `generate_image()`：通过 AiHubMix 代理调用 Gemini（gemini-3.1-flash-image-preview-free），流式返回图像字节
- 图像保存与 `img_entry` 元数据结构（type、id、img_path、img_src_prefix、generated 标记）
- `_build_rewrite_prompt()`：组装 Dify LLM（workflow_id=6）文本重写 prompt
- `_parse_rewrite_output()`：从 LLM 返回中提取 JSON 数组，含降级容错
- 整体 `_enhance_image()` 流程：Gemini 生图 → 保存文件 → LLM 重写要点 → 更新 `visual_refs` 与 `content_points`

#### 4.3.3 基于模板约束的页面布局检测与 HTML 渲染算法

**（1）方法理论**

**模板作为视觉合约**：引入"模板"作为视觉表达的结构化约束层，将页面布局问题从"自由生成"转变为"约束填充"。模板定义三个层面：

- **配色体系**：11 色 BIT 调色板，通过 CSS 变量注入，保证全局视觉一致性
- **CSS 布局骨架**：为每种布局类型提供完整的 CSS 结构定义（定位、分栏、间距、字体、装饰），LLM 在此骨架约束下生成内容 HTML
- **装饰壳层（Shell）**：SVG 几何装饰（梯形 + 色条）、校徽、校训、章节号、标题栏、页脚——与页面内容无关，保证品牌一致性

**布局类型作为语义角色到视觉形式的桥梁**。系统定义 11 种布局类型，分为三大类：

| 类别       | 布局类型                                                     | 适用场景                   |
| ---------- | ------------------------------------------------------------ | -------------------------- |
| 内容驱动型 | text_only, text_image, figure_focus, equation, table_result, conclusion | 由 visual_refs 内容决定    |
| 增强策略型 | text_image_generated, method_cards, setup_timeline, highlight_grid, structured_bullets | 由 visual_enhance 策略决定 |

**布局检测的优先级链**：

增强策略>角色映射>内容类型推断>默认布局增强策略>角色映射>内容类型推断>默认布局



**（2）算法实现**

- `_detect_layout()`：读取 `visual_enhance.strategy` 字段分流——image→`text_image_generated`，css→使用 `css_strategy` 值；无增强标记时按 `role_to_layout`→表格→公式→图片→text_only 逐级推断
- BITContent 模板类：`colors`（11 色）、`layout_css_skeletons`（11 种布局的完整 CSS）、`shell_snippet()`（装饰壳层 HTML 生成）、`system_prompt`（LLM 系统提示词）、`asset_filenames`（logo.png + 校训.svg）
- `_build_prompt()`：组装 Dify LLM（workflow_id=4）渲染 prompt——布局类型 + CSS 骨架 + 装饰壳层 + 内容要点 + 图像/表格/公式数据块 + 配色变量
- `SlideRenderer.render_slide()`：检测布局 → 构建 prompt → LLM 生成 HTML → 去除 markdown 围栏 → 写入文件；含 3 次重试 + 递增等待
- `SlideRenderer.generate_all()`：批量渲染 + 生成 `_viewer.html` 导航页
